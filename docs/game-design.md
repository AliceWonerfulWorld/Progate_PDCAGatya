# Game Design

> Status: Draft / 初版
>
> 本ドキュメントは、PDCA GACHA におけるゲーム要素の初期設計を定義する。
> 現時点ではハッカソンMVPを前提とし、実装コストを抑えながら、
> 「PDCAを回すとガチャを回せる」というコア体験を成立させることを最優先とする。
>
> 詳細な数値バランスやキャラクター設定は、実装・テストを通じて調整する。

---

# 1. ゲーム設計の目的

PDCA GACHA におけるゲーム要素の目的は、ゲームそのものを長時間遊ばせることではない。

目的は、

> **現実世界でPDCAを回した直後に、短期的で分かりやすい報酬を返すこと**

である。

ゲーム要素は以下の役割を持つ。

- PDCAを始めるきっかけを作る
- PDCA完了直後に達成感を与える
- 「もう1周やってみよう」という追加動機を作る
- 長期的な積み上げを可視化する
- 継続するほどキャラクターや世界が育っていく感覚を作る

---

# 2. ゲーム設計原則

## 2.1 PDCAが主役、ゲームは報酬

本プロダクトの主役は現実世界のPDCAである。

ゲーム側だけで完結する設計にはしない。

```text
現実世界でPDCAを回す
↓
報酬を得る
↓
ゲーム世界が少し進む
↓
またPDCAを回したくなる
```

## 2.2 1 PDCA = 1ガチャ

プロダクトの核として、

> **PDCAを1周すると、ガチャを1回回せる**

という対応関係を基本的に維持する。

```text
PDCA 1周
=
ガチャ 1回
```

複雑なポイント交換を挟まず、「回したから回せる」という分かりやすさを優先する。

## 2.3 タスクの結果によって報酬を変えない

以下は同一の基本報酬を得る。

```text
できた
一部できた
できなかった
```

評価するのはタスク達成そのものではなく、

> **CHECK・ACTまで行い、次の行動につなげたこと**

である。

## 2.4 ノルマ感を作らない

ゲーム報酬によって、

> 「今日は3周しないと損」

という状態を作りすぎない。

基本思想は、

> **1周できれば十分。2周目以降はボーナス。**

とする。

## 2.5 長期的にはゲーム世界が成長する

ゲーム部分は以下の段階で拡張可能な設計とする。

```text
Phase 1
キャラクター収集

↓

Phase 2
キャラクター育成

↓

Phase 3
拠点・世界成長
```

MVPでは Phase 1 を完成させる。

# 4. キャラクター収集

## 4.1 MVP方針

MVPでは、

> **キャラクター収集型**

を採用する。

複雑な戦闘、拠点配置、育成システムなどは必須としない。

## 4.2 MVPキャラクター数

初期キャラクター数：

> **15体**

内訳：

| レアリティ | キャラ数 |
|---|---:|
| R | 8 |
| SR | 5 |
| SSR | 2 |
| 合計 | 15 |

キャラクター数は将来的に追加可能とする。

---

# 5. キャラクター世界観

## 5.1 基本コンセプト

キャラクターは、

> **人が何かを続けることで生まれる「継続エネルギー」から生まれた小さな精霊**

という方向性を仮採用する。

PDCAそのものを直接キャラクター化するのではなく、「継続」「成長」「積み上げ」を世界観のモチーフとする。

## 5.2 デザイン方向

MVPでは以下を優先する。

- 小さな精霊・マスコット系
- 一目で区別できるシルエット
- 表情・装飾・性格で個性を出す
- キャラ制作コストを抑えられる構造
- 後から進化・衣装・拠点配置に拡張できる

## 5.3 キャラクターの役割

キャラクターは単なる図鑑要素だけではなく、

> **ユーザーと一緒に継続する相棒**

として扱う。

例：

```text
「今日も1周できたね！」

「できなかった日でも、
振り返れたなら次につながってるよ」

「前回より少し軽くしてみよう」
```

---

# 6. 相棒キャラクター

## 6.1 基本案

ユーザーは所持キャラクターの中から、お気に入りキャラクターを1体設定できる。

MVPでは「全体の相棒1体」を基本とする。

将来的には、

> Goalごとに相棒を設定

できる仕様へ拡張可能とする。

## 6.2 相棒の表示候補

- ホーム画面
- PDCA完了画面
- ストリーク達成時
- リカバリー時
- Player Lv UP時

---

# 7. ガチャ仕様

## 7.1 排出対象

MVPではキャラクターのみ排出する。

アイテム・装備・家具などはガチャに混在させない。

理由：

- ガチャ結果が分かりやすい
- MVPの実装が軽い
- 「新しい相棒を集める」という目的を明確にできる

## 7.2 レアリティ

3段階とする。

```text
R
SR
SSR
```

## 7.3 仮排出率

| レアリティ | 排出率 |
|---|---:|
| R | 70% |
| SR | 25% |
| SSR | 5% |

本数値は仮値であり、実際の継続回数・キャラクター数を見ながら調整する。

## 7.4 1周ごとのガチャ

通常PDCA、リカバリーPDCAともに、

```text
PDCA完了
↓
ガチャ +1回
```

とする。

## 7.5 未使用ガチャ

獲得したガチャ回数は即時消費を強制しない。

```text
ガチャ回数: 3
```

のように保持し、後からまとめて回せる。

MVPでは1回ずつのガチャを基本とし、10連演出は実装余力があれば追加する。

---

# 8. 初回ガチャ

初回ユーザーに良い第一印象を与えるため、初回ガチャには特別仕様を検討する。

候補：

1. SR以上確定
2. 初回専用キャラクター
3. 通常ガチャと同じ完全ランダム

MVP初版では、

> **初回のみSR以上確定**

を有力候補とする。

最終決定は演出・キャラクター制作状況を見て行う。

---

# 9. 重複キャラクター

## 9.1 基本仕様

既に所持しているキャラクターを再度引いた場合、

> **キャラクターの欠片**

へ変換する。

## 9.2 目的

重複を完全なハズレにしないため。

将来的には欠片を、

- Character Lv上昇
- 進化
- 覚醒
- 特別衣装
- キャラクター演出解放

などへ利用できる。

## 9.3 欠片量

現時点ではTBD。

仮案：

| レアリティ | 重複時の欠片 |
|---|---:|
| R | 10 |
| SR | 20 |
| SSR | 40 |

ゲームバランス確定時に再検討する。

---

# 10. Player XP

## 10.1 役割

Player XPは、

> **ユーザー自身がどれだけPDCAを回してきたか**

を表す経験値。

キャラクター育成経験値とは分離する。

## 10.2 XP獲得

基本：

```text
PDCA 1周
→ Player XP +100
```

数値は仮値。

DOの成功・失敗によって基本XPは変化しない。

## 10.3 追加XP

以下の行動に対する少量ボーナスは検討可能。

- 詳細CHECKを行う
- 自由記述を行う
- 初回PDCA
- デイリーミッション達成
- ウィークリーミッション達成

ただし、

> XPのために長文入力を強制する

状態にはしない。

---

# 11. Player Lv

## 11.1 意味

Player Lvは単なるゲームレベルではなく、

> **PDCAを回してきた経験・習熟度**

を表現する。

## 11.2 レベルアップ報酬

Player Lv上昇によって、以下の3系統の報酬を提供する。

### 1. 称号

例：

```text
Lv.1  はじめの一周
Lv.5  習慣のたまご
Lv.10 Cycle Runner
Lv.20 Improver
```

名称は仮。

### 2. Progressive PDCA機能解放

基本機能をロックするのではなく、

> **レベルが上がるほど、より深くPDCAを回せる**

ようにする。

例：

```text
Lv.1
基本CHECK

Lv.5
CHECK原因分析

Lv.10
Goal別傾向表示

Lv.15
過去履歴を使ったAI改善提案

Lv.20
月間PDCAレポート
```

具体的な解放レベルはTBD。

### 3. ガチャ報酬

節目のPlayer Lvで追加ガチャを付与する。

例：

```text
Lv.5
ガチャ +1

Lv.10
ガチャ +3

Lv.20
ガチャ +5
```

数値は仮。

## 11.3 レベルアップ演出

例：

```text
PLAYER LEVEL UP!

Lv.4 → Lv.5

🏷️ 称号
「習慣のたまご」

🔓 詳細CHECK 解放

🎫 ガチャ +1
```

PDCA完了とは別の中期的な達成イベントとして扱う。

# 12. Player Lvのレベルカーブ

具体的な必要XPは未確定。

基本方針：

> 序盤はテンポよく上がり、長期になるほど必要XPが少しずつ増える。

固定1000XPごとのような完全一定制より、緩やかな増加カーブを検討する。

例：

| Level | 必要累計XP |
|---|---:|
| 1 | 0 |
| 2 | 300 |
| 3 | 700 |
| 4 | 1,200 |
| 5 | 1,800 |
| 10 | TBD |
| 20 | TBD |

最終数値は実装・テスト時に決定する。

# 13. Character XP / Character Lv

## 13.1 Player XPとの分離

```text
Player XP
→ ユーザー自身

Character XP
→ キャラクター個別
```

として別管理する。

## 13.2 MVP優先度

Player XP / Player Lv：

> **MVP必須**

Character XP / Character Lv：

> **MVPでは余裕があれば実装**

とする。

## 13.3 将来案

キャラ重複で得た欠片を使用して、

```text
欠片
↓
Character XP
↓
Character Lv UP
```

または直接Lvを上げる方式を検討する。

# 15. デイリーミッション

## 15.1 目的

毎日の継続リズムを作る補助要素。

ノルマ化しないことを重視する。

## 15.2 MVP案

基本デイリー：

```text
今日のチャレンジ

PDCAを1周する

報酬:
Player XP +50
```

## 15.3 位置付け

通常PDCA報酬が主役。

```text
通常報酬
Player XP + ガチャ

+

デイリーボーナス

```

とする。

デイリー未達によって大きく損をする設計にはしない。

# 17. ミッション設計原則

デイリー / ウィークリーでは以下を避ける。

```text
毎日3周しないと未達
毎日HARDタスクを実行
特定Goalを必ず実施
```

「やらないと損」という圧力が強くなるため。

基本的には、

> **普段のPDCAを続けていれば自然に達成できる**

程度の難易度とする。

# 18. ガチャの大量周回への対応

本プロダクトでは、

```text
1 PDCA = 1ガチャ
```

のため、通常のソーシャルゲームよりガチャ回数が多くなる可能性がある。

## 18.1 基本方針

PDCA側に強いハード上限を設けることで解決しない。

ゲーム側を、

> **大量にガチャを回しても意味が残る構造**

へ拡張する。

## 18.2 対応策

### MVP

- キャラ収集
- 重複 → 欠片
- コレクション率

### Phase 2

- Character Lv
- キャラ進化
- 欠片消費
- キャラごとの親密度

### Phase 3

- 拠点成長
- 家具
- 建物
- キャラクター配置
- 世界の拡張

# 19. 天井・確定枠

MVPでは本格的な天井システムを必須としない。

理由：

- 課金ガチャではない
- 1PDCAごとに無料で引ける
- 実装コストに対してMVP価値が低い

ただし、

> 長期間SSRが出ないユーザーへの体験悪化

が確認された場合は、

```text
30回以内にSSR確定
```

などのソフト天井を検討する。

---

# 20. 課金について

MVPでは課金要素を実装しない。

特に、

> お金を払ってガチャ回数を購入する

仕様は、PDCAとガチャの関係を弱めるため採用しない。

ガチャは、

> **現実世界でPDCAを回した報酬**

として扱う。

# 26. ゲーム設計上の判断基準

新しいゲーム機能を追加する際は、以下を確認する。

1. PDCAを回したくなる理由になるか
2. ゲームだけを遊ぶ状態にならないか
3. 「今日は1周だけ」を邪魔しないか
4. ノルマ感を強くしすぎていないか
5. タスク未達ユーザーを罰していないか
6. 長期的な継続に意味が残るか
7. 実装コストに対して体験価値があるか
8. ゲーム要素がPDCA体験より主役になっていないか

# 27. 目指すゲーム体験

最初は、

> **「ガチャを回したいから、とりあえず1周する」**

という短期的な動機でよい。

PDCAを続けるうちに、

```text
ガチャを回したい
↓
キャラクターを集めたい
↓
Player Lvを上げたい
↓
相棒に愛着が湧く
↓
自分の積み上げを止めたくない
↓
PDCAを回すこと自体が習慣になる
```

という形で、継続理由が少しずつ変化していくことを目指す。

最終的には、

> **ゲームのために始めたPDCAが、いつの間にかユーザー自身の習慣になっている**

状態を理想とする。
