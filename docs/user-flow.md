# User Flow

> Status: Draft / 仮仕様
>
> 本ドキュメントは、PDCA GACHA のユーザーフロー初版を定義する。
> 現時点では「継続のためにユーザー負担を極限まで軽くする」ことを最優先し、細部はレビュー後に変更する前提とする。

---

## 0. UX設計原則

本フローでは以下を共通原則とする。

* 説明する前に、まず1周体験してもらう
* 初回登録・プロフィール入力を最初の価値体験より前に置かない
* 基本操作はタップ中心とし、自由記述は任意とする
* タスクの達成・未達そのものを評価しない
* 「今日は少しだけ」を常に許容する
* AIはユーザーの代わりに考える補助役とし、最終決定はユーザーが行う
* PDCA完了後は必ず即時報酬を返す
* 失敗したユーザーを責めず、次の行動へ戻しやすくする
* 1周で十分。2周目以降は追加でできた成果として扱う

---

# 1. 初回起動・オンボーディング

## 1.1 目的

ユーザーに長い説明を読ませず、最短距離で最初のPDCAへ到達させる。

## 1.2 初回画面

表示内容は最小限とする。

```text
PDCA GACHA

PDCAを回したら、ガチャを回せる。

[ はじめる ]
```

長いチュートリアル、機能一覧、詳細なPDCA説明は表示しない。

## 1.3 アカウント登録

最初のPDCA・ガチャ体験より前には必須としない。

初回ガチャ後に必要であれば、

```text
この記録を残しますか？

[ 保存する ]
[ あとで ]
```

のような導線を設ける。

認証方式そのものは technical-design 側で決定する。

## 1.4 初回フロー

```text
アプリ起動
↓
はじめる
↓
Goal作成
↓
AIによる初回PLAN候補
↓
PLAN確定
↓
DO
↓
CHECK
↓
ACT
↓
PDCA COMPLETE
↓
初回ガチャ
↓
ホーム
```

---

# 2. Goal作成

## 2.1 目的

ユーザーが「継続したいこと」を最小入力で登録する。

## 2.2 入力

基本的に1項目のみとする。

```text
何を続けたい？

[ 英語学習                    ]

[ 次へ ]
```

以下は初回登録時には要求しない。

* 期間
* 数値目標
* カテゴリ
* 1日の目標時間
* 達成条件
* 継続理由

## 2.3 Goal作成後

Goal名をもとにAIが最初のPLAN候補を1つ生成する。

例：

```text
英語学習ですね。
まずはこれくらいからどうですか？

「英単語を5個覚える」

[ もっと軽く ]
[ これでやる ]
[ もう少しやる ]
[ 自分で決める ]
```

AIが利用できない場合は、Goal名をそのまま利用した簡易PLAN、またはユーザー入力へフォールバックする。

---

# 3. ホーム画面

## 3.1 目的

「今日何をすればいいか」を一目で分かる状態にする。

情報を詰め込みすぎず、PDCA開始を最優先CTAとする。

## 3.2 基本表示

```text
🔥 Streak 14日
今日のPDCA 0周

今日も1周だけ回そう。

--------------------
英語学習
次の候補：英単語を5個復習する
[ PDCAを回す ]
--------------------

個人開発
次の候補：ログインAPIを接続する
[ PDCAを回す ]
--------------------
```

## 3.3 ホームで優先表示する情報

* 現在のストリーク
* 今日のPDCA周回数
* Goal一覧
* Goalごとの次回PLAN候補
* 進行中PDCAがある場合はその続き

ガチャ、履歴、コレクションなどはセカンダリ導線とする。

## 3.4 進行中PDCA

DO中のPDCAが存在する場合、ホーム上部に優先表示する。

```text
いま DO            (P) (D) (C) (A)

英語学習
英単語を5個覚える

[ 振り返る ]
```

現在地の表示とCTA文言は ui-spec #7.1 / #7.2 に従う。

---

# 4. PLAN開始

## 4.1 2回目以降

前回のACT・CHECK・履歴をもとに、次のPLAN候補を提示する。

```text
今日これやる？

英単語を5個復習する

前回は少し重かったため、
前回より軽めにしています。

[ もっと軽く ]
[ これでやる ]
[ もう少しやる ]
[ 自分で変更 ]
```

## 4.2 タスクサイズ

LIGHT / NORMAL / HARD のような分類をユーザーには選ばせない。

負荷調整は相対表現のみとする。

```text
もっと軽く
これでやる
もう少しやる
自分で変更
```

## 4.3 PLAN確定

「これでやる」を選択するとDO開始画面へ進む。

---

# 5. DO中

## 5.1 開始

```text
今日やること

英単語を5個覚える

[ 開始する ]
```

「開始する」でDO状態を保存する。

## 5.2 DO中画面

```text
DO

英単語を5個覚える

終わったら戻ってきてください。
アプリは閉じても大丈夫です。

[ 振り返る ]
```

DO中はユーザーの作業を邪魔しない。

* アプリを閉じてよい
* 常時タイマーを要求しない
* 入力を要求しない
* DO状態は保持する

## 5.3 DO終了

ユーザーが「振り返る」を押したら結果を選択する。

```text
どうだった？

[ できた ]
[ 一部できた ]
[ できなかった ]
```

どれを選んでもCHECKへ進む。

「できなかった」は失敗扱いにしない。

---

# 6. CHECK

## 6.1 基本CHECK

最初にタスク負荷を確認する。

```text
今回どうだった？

[ 余裕だった ]
[ ちょうどよかった ]
[ 少し重かった ]
[ かなり重かった ]
```

## 6.2 条件付き深掘り

必要な場合のみ追加質問を出す。

例：重かった / できなかった場合

```text
何が原因だった？

[ 時間がなかった ]
[ タスクが大きすぎた ]
[ 難しかった ]
[ 集中できなかった ]
[ やる気が出なかった ]
[ その他 ]
```

余裕・ちょうどよかった場合は、追加質問をスキップしてACTへ進んでもよい。

## 6.3 自由記述

任意でメモを追加できる。

```text
+ メモを追加
```

自由記述を必須にはしない。

---

# 7. ACT

## 7.1 目的

今回の結果を次のPLANへ接続する。

## 7.2 基本表示

CHECKをもとにシステムが推奨ACTを提示する。

例：

```text
次はどうする？

おすすめ
● 少し軽くする

○ そのまま
○ 少し増やす
○ やり方を変える

[ これでいく ]
```

## 7.3 具体PLAN候補

可能であればACT選択時点で次回PLAN候補をプレビューする。

```text
次回はこんな感じにします。

英単語10個
↓
英単語5個

[ これでいく ]
[ 調整する ]
```

AIが利用できない場合はルールベースの相対調整のみ保存する。

## 7.4 ACT確定

ACTを確定した時点でPDCAを1周完了とする。

---

# 8. PDCA完了

## 8.1 完了演出

ACT確定直後に即時フィードバックを返す。

```text
PDCA COMPLETE!

🔄 +1周
⭐ +100 XP
🎫 ガチャ +1回
```

その日の1周目の場合は追加で、

```text
🔥 今日のストリーク達成！
```

を表示する。

## 8.2 結果の扱い

DOが「できなかった」であっても、CHECK・ACTまで完了していれば同じ完了演出・基本報酬を与える。

## 8.3 次のCTA

Primary:

```text
[ ガチャを回す ]
```

Secondary:

```text
[ あとで回す ]
```

---

# 9. ガチャ

## 9.1 基本フロー

```text
ガチャを回す
↓
短い演出
↓
報酬表示
↓
コレクション反映
```

PDCA 1周につきガチャ1回を基本とする。

## 9.2 報酬表示後

```text
NEW!
キャラクター / アイテム

[ もう1周する ]
[ ホームへ ]
```

「もう1周する」は強制しない。

## 9.3 ガチャを後回しにした場合

未使用ガチャ回数として保持する。

ホーム等から後で回せる。

---

# 10. 次のPLANへの戻り方

## 10.1 基本

PDCA完了後は一度区切りを作る。

自動で次のPDCAを開始しない。

これは、

> **1周できた時点で今日の成功**

という体験を守るためである。

## 10.2 「もう1周する」

ユーザーがもう1周を選んだ場合、直前のACTから生成された次回PLAN候補を表示する。

```text
次はこれで回す？

英単語を5個復習する

[ もっと軽く ]
[ これでやる ]
[ もう少しやる ]
[ 自分で変更 ]
```

同じGoalで続けても、別Goalを選んでもよい。

## 10.3 ホームへ戻った場合

Goalカード上に次回PLAN候補を保持する。

次回アクセス時にゼロからPLANを考え直させない。

---

# 11. ストリーク危機時

## 11.1 危機状態への移行

ユーザーのローカル日付を基準に、前日にPDCA完了が0周だった場合、翌日にストリークを即時リセットせず「危機状態」とする。

```text
🔥 14日ストリーク
⚠️ STREAK AT RISK
```

## 11.2 表示

責める表現は使わない。

```text
昨日はPDCAを回せなかったようです。
まだストリークを戻せます。

[ リカバリーする ]
[ あとで ]
```

ホーム全体をブロックするモーダルにはせず、目立つカード・バナーとして表示する。

## 11.3 仮のリカバリー制限

初版では、

> **直近7日間に1回まで**

リカバリー可能とする。

この値はゲームバランス確認後に変更可能とする。

## 11.4 本当にストリークが切れる条件

以下のいずれかでストリーク終了とする。

```text
前日0周
↓
翌日のローカル日付終了までに
リカバリーPDCAを完了しなかった
```

または、リカバリー利用条件を満たしていない場合。

---

# 12. リカバリーPDCA

## 12.1 目的

ストリークを無条件で免除するのではなく、継続できなかったこと自体を次の改善材料にする。

## 12.2 STEP 1: CHECK

```text
昨日、回せなかった理由は？

[ 忙しかった ]
[ 疲れていた ]
[ 忘れていた ]
[ 体調が悪かった ]
[ タスクが重かった ]
[ その他 ]
```

## 12.3 STEP 2: 今日のPLAN候補

理由をもとに、通常より軽いPLANを提案する。

```text
今日はこれだけやってみよう。

英単語を3個だけ復習する

[ もっと軽く ]
[ これでやる ]
[ 自分で変更 ]
```

## 12.4 STEP 3: DO

通常PDCAと同じく実行する。

結果は、

```text
できた
一部できた
できなかった
```

から選ぶ。

## 12.5 STEP 4: 簡易CHECK / ACT

```text
このくらいなら続けられそう？

[ もっと軽くする ]
[ このまま ]
[ 少し増やす ]
```

完了するとリカバリー成立。

## 12.6 リカバリー成功時

```text
STREAK RECOVERED!

🔥 14日ストリークを維持しました
🔄 今日のPDCA +1周
⭐ XP
🎫 ガチャ +1回
```

リカバリーPDCAは実際に1つのPDCAを回しているため、今日の1周としてもカウントする。

通常PDCAと同様に基本報酬を与える。

これにより、復帰した当日にさらに別のPDCAを強制しない。

---

# 13. 履歴・成長確認

## 13.1 目的

結果の優劣ではなく、「どれだけ回してきたか」を可視化する。

## 13.2 全体サマリー

最低限以下を表示する。

```text
🔥 現在のストリーク
14日

🔄 今日
3周

🔄 今週
12周

🔄 累計
128周
```

## 13.3 Goal詳細

```text
英語学習

累計PDCA: 42周
活動日数: 18日

最近のPDCA
----------------
英単語10個 → 少し重かった
次回: 5個にする

英単語5個 → ちょうどよかった
次回: そのまま
----------------
```

## 13.4 履歴で強調しないもの

「成功率」「失敗回数」のような、できなかったことを強くネガティブ評価する指標はメイン表示にしない。

必要であれば改善材料として内部利用する。

## 13.5 将来的な成長表示

MVP後の候補として、

* PDCAレベル
* 振り返り傾向
* タスク負荷の変化
* 継続パターン
* 「最近タスク分割が上手くなった」等のフィードバック

を検討する。

# 15. 初回体験の理想

初回ユーザーには、アプリの機能を理解してもらうことよりも、

> **「本当にPDCAを回したらガチャが回せた」**

という体験を最優先する。

そのため初回は、

```text
Goal入力
↓
AIがPLANを提案
↓
実行
↓
数タップでCHECK / ACT
↓
ガチャ
```

までを可能な限り短くする。

初回PDCAが完了した後に初めて、

* ストリーク
* 履歴
* 複数Goal
* 詳細CHECK
* コレクション

などの追加機能を段階的に認知させる。

---

# 16. 現時点の仮決定事項

* 初回オンボーディングは最小限
* 初回Goal作成はGoal名のみ
* 初回PLANはAIが候補を提示
* PLAN負荷は相対調整のみ
* DO中はアプリが介入しない
* DO未達でも通常通りCHECKへ進む
* CHECKは1〜数タップ中心
* ACTから次回PLANへ接続する
* ACT完了時点でPDCA成立
* 1周ごとにXP + ガチャ1回
* その日の1周目でストリーク達成
* PDCA周回数は無制限
* PDCA完了後に次の周回を強制しない
* ストリーク未達翌日は危機状態
* リカバリーは仮で直近7日間に1回
* リカバリーPDCAは今日の1周としても扱う
* リカバリーPDCAにも通常報酬を付与する
* 履歴では成果よりPDCAの積み上げを強調する

---

# 17. レビュー時に確認したいポイント

1. 初回起動からガチャまでに不要なステップがないか
2. ホーム画面に情報を出しすぎていないか
3. PLANのAI提案がユーザーの自由度を奪っていないか
4. DO終了からACT完了までが十分軽いか
5. CHECKの質問数が多すぎないか
6. PDCA完了後にガチャへ直行する体験が自然か
7. 「もう1周」の導線が継続を強制する表現になっていないか
8. ストリーク危機状態がユーザーを責める設計になっていないか
9. リカバリーPDCAが重すぎないか
10. リカバリーを今日の1周として扱う仕様が適切か
11. 7日に1回という救済頻度が適切か
12. 履歴・成長表示が「結果主義」になっていないか
