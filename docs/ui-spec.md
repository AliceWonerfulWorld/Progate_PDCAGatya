# UI Specification

> Status: Draft / 初版
>
> 本ドキュメントは、PDCA GACHA のMVPにおけるUI仕様を定義する。
>
> `product-spec.md` が機能仕様、`user-flow.md` が遷移・体験フローを定義するのに対し、
> 本ドキュメントでは「各画面に何を表示し、ユーザーが何を操作できるか」を画面単位で整理する。
>
> 基本思想は一貫して、
>
> > **考える負担はシステム側、決める権利はユーザー側。**
>
> とする。

---

# 1. UI設計原則

PDCA GACHA のUIは以下を最優先とする。

1. 1周を始めるまでの操作を少なくする
2. PDCA中はユーザーに長文入力を要求しない
3. 基本操作はタップ中心にする
4. DO中はアプリが邪魔をしない
5. 日常操作は静かに、報酬演出は気持ちよくする
6. 「できなかった」ことをネガティブに強調しない
7. 1周できた時点で「今日の成功」と感じられるUIにする
8. ゲーム要素はPDCAより前面に出しすぎない
9. モバイルファーストで設計する
10. PWAとしてホーム画面から素早く使える体験を目指す

---

# 2. Navigation

## 2.1 Bottom Navigation

メイン画面では下部固定ナビゲーションを使用する。

MVPでは4タブとする。

```text
Home
Collection
History
Profile
```

### 表示方針

- アイコン中心
- 選択中タブのみラベル表示を許容
- 未選択タブはアイコンのみでもよい
- タブ数は増やしすぎない
- ガチャは常設タブにしない

### 理由

ガチャを独立した主要画面として常設すると、
ゲーム部分がプロダクトの主役に見えやすいため。

未使用ガチャがある場合のみ、
Home上に目立つCTAを表示する。

## 3.2 表示要素

```text
PDCA GACHA
```

## 3.3 表示しないもの

- 長いチュートリアル
- PDCAの詳細説明
- 機能一覧
- 認証フォーム
- 通知許可
- プロフィール入力
- 詳細設定

## 3.4 Primary CTA

```text
はじめる
```

Goal作成画面へ遷移する。

# 4. Goal作成画面

## 4.1 目的

ユーザーが継続したい対象を最小入力で登録する。

## 4.2 UI

```text
何を続けたい？

[ 英語学習                    ]

[ 作成する ]
```

## 4.3 必須入力

- Goal名のみ

## 4.4 初回では要求しない情報

- カテゴリ
- 目標時間
- 数値目標
- 期限
- 達成条件
- 継続理由

## 4.5 バリデーション

### 空欄

```text
続けたいことを入力してください
```

### 長すぎる入力

入力上限を設け、
モバイルで1〜2行に収まりやすい文字数を推奨する。

具体値は実装時に決定する。

## 5.1 目的

ユーザーがゼロから最初のPLANを考えなくてよい状態を作る。

## 5.2 UI例

```text
最初の一周を回してみよう

英語学習なら、
まずはこれくらいからどう？

英単語を5個覚える

[ もっと軽く ]

```

## 5.3 AI表示方針

「AIが生成しました」等を大きく表示しない。

重要なのはAI利用そのものではなく、

> **すぐ始められること**

である。

```text

```

へフォールバックする。

エラー文を大きく出さない。

# 6. Home

## 6.1 目的

ユーザーが、

> **今日何をすればいいか**

を一目で理解できる画面。

情報閲覧よりも、
次のPDCA開始を優先する。

---

## 6.2 優先順位

Home上では以下の優先度で情報を表示する。

1. 進行中PDCA
2. ストリーク危機
3. 今日の1周導線
4. Goal / 次回PLAN候補
5. Streak / 今日の周回数
6. Player Lv
7. 相棒キャラ
8. 未使用ガチャ
9. その他の情報

---

## 6.3 基本構成

Homeは「今日やる1周」に集中させる。
Goalや報酬導線が増えても縦に伸び続けないよう、
情報は以下の4ブロックに固定する。

```text
────────────────────
今日の一歩
今日も1周だけ回そう          [相棒キャラ]
🔥 14日   🔄 今日 0周
「今日も1周だけやろう」
────────────────────

(進行中PDCAがあればここに1枚)
(ストリーク危機があればここに1枚)

続けたいこと
今日の1周を始めよう

英語学習
次の候補: 英単語を5個復習する
[ PDCAを回す ]

個人開発
次の候補: ログインAPIを接続する

読書
次の候補: 10ページ読む

▼ 他 2 件のGoalを見る

+ Goalを作る
────────────────────
○ 1周で +50 XP        🎫 ガチャ 2回を回す
────────────────────
```

### 6.3.1 相棒キャラの表示枠

相棒キャラとマスコットは同じ役割のため、
ヘッダー右側の1枠に統合する。

相棒が未設定（初回ガチャ前）の場合のみ、
デフォルトマスコットがその枠に入る。

### 6.3.2 Goal一覧の畳み込み

Goalは先頭3件までを表示し、
それ以上は「他 N 件のGoalを見る」で畳む。

開始CTA（`PDCAを回す`）は先頭Goalにのみ表示する。

理由：

- 同格のCTAを並べると「今日どれをやるか」の判断をユーザーへ丸投げすることになる
- Goalが増えるほどHomeが縦に伸び、今日の1周が画面外へ押し出される

2件目以降のGoalはタップでGoal詳細へ遷移し、
そこからPDCAを開始できる。

### 6.3.3 進行中PDCAがある場合

進行中Cycleが存在する場合、
再開カード（現在地に応じたCTA、#7.2）をGoal一覧より上に表示する（AC-HOME-001）。

Goal一覧の開始CTAは残す。

MVPは複数同時進行を許可する（#7）ため、
進行中の1周とは別のGoalを新しく始める導線を塞がない。

見出しは `他のGoal` に変わり、
再開カードとの重複を避ける。

### 6.3.4 報酬ステータスバー

今日のチャレンジ（Mission）と未使用ガチャは、
画面下部の1行の帯にまとめる。

どちらも「今日やること」そのものではない補助情報のため、
カードとして縦を消費させない。

未使用ガチャが0回の場合、ガチャ導線は表示しない。

---

## 6.4 今日0周の場合

文言例：

```text
今日も1周だけ回そう。
```

「最低○周」等の表現は使用しない。

---

## 6.5 今日1周以上の場合

文言例：

```text
今日の1周、達成済み！
余裕があればもう1周。
```

複数周回を強制する表現にしない。

# 7. Home - 進行中PDCA

進行中のPDCAが存在する場合、
Home上部に最優先で表示する。

```text
いま DO            (P) (D) (C) (A)

英語学習
英単語を5個復習する

[ DOを開く ]
```

Goal一覧より上に表示する。

## 7.1 現在地の表示

`status` は「完了したフェーズ」ではなく
「いまいるフェーズ」を表す。

P / D / C / A の4点で現在地を示す。

```text
status = doing     → D が現在地、P は完了済み
status = checking  → C が現在地、P / D は完了済み
status = acting    → A が現在地、P / D / C は完了済み
```

PLANはCycle作成時点で確定済みのため（#12）、
Pは常に完了済みとして表示される。

## 7.2 CTA文言

`続きを開く` のような汎用文言は、
いまどのフェーズなのかを伝えない。

現在地に応じた次の一手を示す。

```text
doing     → DOを開く
checking  → 振り返る
acting    → 次のPLANを決める
```

`doing` は「まだ実行していない」と
「実行して結果を報告する」の両方を含むため、
どちらにも当てはまる文言にする。

（この2つの区別はDO画面のローカル状態であり、
サーバー側には保持しない。）

## 7.3 複数同時進行

MVPでは1つの進行中PDCAを推奨する。

複数同時進行を許可するかどうかは
technical-design 側で確定する。

```text
でも、まだ戻せます。

[ リカバリーする ]
```

以下のような責める表現は避ける。

```text

```


---

## 9.3 Primary CTA

```text

```

---

## 9.4 タスクサイズ

UI上では以下を表示しない。

```text

NORMAL

```

ユーザーにカテゴリ判定を要求せず、

```text

```

## 9.5 自分で変更

`自分で変更` を押した場合のみ入力欄を展開する。

初期表示からテキスト入力欄を見せない。

```text
今日やること

[ 英単語を5個復習する       ]

[ このPLANで進む ]
```

# 12. DO結果画面

## 12.1 UI

```text
どうだった？

[ できた ]
[ 一部できた ]
[ できなかった ]
```

## 12.2 重要ルール

どの選択肢も同じCHECKフローへ進む。

「できなかった」を赤色・エラー表現で強調しない。

---

# 13. CHECK画面

## 13.1 基本CHECK

```text
今回どうだった？

[ 余裕だった ]
[ ちょうどよかった ]
[ 少し重かった ]
[ かなり重かった ]
```

最短1タップで終了可能にする。

---

## 13.2 条件付き深掘り

以下の場合に追加質問を表示する。

- 少し重かった
- かなり重かった
- DOで「できなかった」
- 必要と判断された場合

例：

```text
何が原因だった？

[ 時間がなかった ]
[ タスクが大きすぎた ]
[ 難しかった ]
[ 集中できなかった ]
[ やる気が出なかった ]
[ その他 ]
```

---

## 13.3 自由記述

常に任意。

```text
+ メモを追加
```

入力しなくても次へ進める。

---

## 13.4 Progressive UI

Player Lv等によって高度なCHECKが解放された場合も、
基本CHECKを消さない。

高度機能は追加選択として提供する。

---

# 18. Gacha - 演出画面

## 18.1 目的

PDCA完了の報酬として、
短く気持ちのよい演出を返す。

---

## 18.2 演出時間

目安：

> **1〜2秒程度**

何度も回す前提のため、
長すぎるスキップ不可演出は避ける。

---

## 18.3 レアリティ差

```text
R
通常演出

SR
少し豪華

SSR
明確に特別
```

SSRでは、

- 光量
- パーティクル
- 専用SE
- 一瞬の溜め

などで差を出す。

# 36. Color / Visual Direction

実体は `src/index.css` の `@theme` に定義したデザイントークンとする。
以下は方針であり、**値の参照元はコードのトークン定義**（issue #97）。

## 基調色（Primary）

事実上のPrimaryとして使われていた emerald 系（`oklch(50.8% 0.118 165.612)`）を
ブランドカラーとして正式採用し、`--color-primary` とした。

## 色の役割

| 役割 | トークン接頭辞 | 用途 |
| --- | --- | --- |
| Primary | `primary` | CTA・アクティブ状態・フォーカスリング |
| Surface / Text / Border | `surface` / `text` / `border` | 日常画面の面・文字・境界 |
| Rarity | `rarity-r` / `rarity-sr` / `rarity-ssr` | ガチャのレアリティ。SSRのみ `rarity-ssr-glow` で光彩 |
| At Risk | `attention` | Streak At Risk の注意喚起 |
| Gacha / Reward | `reward` | ガチャ・チケットなど報酬系の差し色 |
| Choice | `choice-info` / `choice-warn` | 選択トグル。レアリティ色とは別系統 |

Rarity と Choice は現状いくつか同系色だが、**意図的に別トークン**にしている。
片方の色を変えたときにもう片方が巻き添えで変わるのを防ぐため。

## モーション

duration は `--duration-instant / fast / normal / slow / reward`、
easing は `--ease-standard / decelerate / accelerate / spring` の5段・4種。

`prefers-reduced-motion: reduce` はトークン層で duration を 0 に差し替えて吸収する。
個別コンポーネントでの対応は不要。

> **注意**: Tailwind v4 では `--duration-*` はユーティリティ生成の namespace ではないため、
> `duration-fast` とは書けない。必ず `duration-(--duration-fast)` の形で参照すること。
> `duration-150` のような数値ユーティリティは値を焼き込むため reduced-motion が効かない。

基本方針：

- 日常画面は落ち着いたUI
- Primary CTAは一目で分かる
- レアリティは識別しやすくする
- SSRだけ特別感を強くする
- 「できなかった」を警告色で責めない
- Streak At Riskは注意喚起するが恐怖訴求しない

# 37. Typography

基本方針：

- モバイルで読みやすい
- 見出しと本文の階層を明確にする
- 長文を極力表示しない
- Primary CTAを大きくする
- 数値（Streak / Lv / 周回数）は視認性を高くする

# 38. Touch Target

スマートフォン操作を前提に、

- タップ領域を小さくしすぎない
- 主要選択肢は片手で押しやすくする
- 重要CTAを画面下部付近に配置する
- 選択肢を密集させすぎない

ことを重視する。

# 42. UI実装上の判断基準

新しいUI要素を追加する際は、
以下を確認する。

1. この情報は今この画面で必要か
2. ユーザーに新しい判断を増やしていないか
3. 入力を減らせないか
4. 「今日は少しだけ」を邪魔していないか
5. PDCA開始までの距離を伸ばしていないか
6. 未達ユーザーを責める表現になっていないか
7. ゲーム部分を主役にしすぎていないか
8. スマホで片手操作しやすいか
9. 1タップ減らせないか
10. アニメーションがテンポを悪化させていないか

# 43. 最終方針

PDCA GACHA のUIは、

> **多機能に見せること**

ではなく、

> **気付いたらPDCAを1周していた**

という状態を目指す。

そのため、

```text
Home
↓
PLAN候補を選ぶ
↓
DO
↓
数タップでCHECK
↓
数タップでACT
↓
PDCA COMPLETE
↓
ガチャ
```

という一連の操作を、
可能な限り短く・迷わず・気持ちよく完了できることを最優先とする。

特に、

> **日常操作はシンプルに。報酬体験だけ派手に。**

をUI全体の基準とする。
